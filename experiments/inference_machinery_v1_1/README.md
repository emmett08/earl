## Question and estimands

For twelve purposively authored synthetic argument snapshots at a fixed
evaluation time, does the actual EAL/2 evaluator return the independently
specified bounded claim status? Does adding that computed status and trace to
otherwise identical raw evidence improve one small model's answers on these
same cases? These are different measurements:

* **Engine accuracy:** number of exact EAL/2 statuses matching the project
  author's pre-run `oracles.json`, divided by twelve. An EAL/2 result is never
  the oracle. An error remains in the denominator.
* **Agent pilot:** number of exact case statuses in the EAL-assisted session
  minus the number in the raw-evidence session. The unit assigned to each arm
  is one fresh model session covering all twelve cases. Cases within a session
  are dependent repeated measurements, not twelve independent agents.

The two arms use the same model, low reasoning effort, developer instruction,
case order, observation values and prose rule contract. Neither receives the
oracle. The raw arm must compute each conclusion; the assisted arm sees the
**real EAL/2 evaluation and ASPIC+ compilation** from those same observations.
It receives no selected engineering action or answer generated by a host
oracle. The difference is access to a checked computed result and trace, not
EAL notation alone. The agent contrast assesses usefulness of that aid; it
cannot separate the value of EAL's specific algorithm from the value of any
accurate checked answer. A conventional checked-result comparator would be
needed for that further question.

## Case contract and oracle

The bounded synthetic finding concerns `site=bench`. The current calibrated
direct test supports one route; an alternate current test supports an
independent route. A current trace gap attacks only the first route; a current
rebuttal defeats that objection. A current global blocker attacks the claim.
The evidence age limit is 60 seconds. Missing and stale observations do not
become false assertions. A different site is out of scope. The four exact
statuses are `supported`, `contested`, `unsupported` and `out_of_scope`.

`argument.eal` encodes those relations. `cases.json` contains twelve source
snapshots including targeted undercut, independent-route rescue, claim-level
attack, defence, expiry, missing calibration and changed scope. `oracles.json`
was reasoned from the prose contract and fixed before an agent call. Both are
project-authored; an external blind adjudicator has **not** validated their
representativeness or the informal warrant. `run.py prepare` checks every
case with the actual interpreter and compiler and reports disagreements
without dropping or rewriting them. Testing that implementation on authored
cases supports a bounded software result, not the truth of an engineering
claim in a production system.

## Interpretation fixed before live acquisition

| Observation | Permitted reading |
|---|---|
| EAL disagrees with an independently reviewed oracle | Investigate semantics, evidence binding or the oracle. Preserve the mismatch; no superiority claim. |
| Raw agent wrong, aided agent correct on one or more cases | A local benefit of access to this checked result on these cases, subject to engine correctness and an intact prompt. |
| Raw agent correct, aided agent wrong | A local adverse effect of the aid, including possible over-reliance. |
| Both arms answer all cases correctly | Endpoint ceiling; no observed added value and no equivalence finding. |
| Both arms err or results are mixed | Report exact case-level differences and mechanisms; no single-direction benefit claim. |
| Either call fails, is truncated, invalid or has incomplete usage | Preserve the attempt and mark the paired agent result unavailable; no automatic paid retry. |

No `p` value, confidence interval, population performance claim, technical-debt
claim or architecture claim follows from one session per arm. The explicit
mechanism contrast answers a finite question; a general effect requires
independently chosen problems and more independently assigned sessions.

## Running and cost guard

The `inference-machinery-v1-1.yml` workflow validates on ordinary pushes and
makes **zero API calls** then. Paid execution is possible on manual workflow
dispatch with `live=true`, or on the single activation commit whose message is
exactly `Run inference machinery pilot v1.1`. Retries of that run skip the paid
job. Locally:

```sh
python -m pip install -e '.[dev]'
python -m pytest -q experiments/inference_machinery_v1_1/test_inference.py
python experiments/inference_machinery_v1_1/run.py prepare --output /tmp/eal-inference
CODEX_API_KEY=... python experiments/inference_machinery_v1_1/run.py live \
  --live --output /tmp/eal-inference-live
```

The pilot makes at most **two Responses API requests**, one per arm, with
`gpt-5.4-nano`, no tools or persistent server-side conversation, at most
32,000 UTF-8 request bytes and 2,200 output tokens per request. The local
preflight and between-call guard enforce a USD 0.03 **conditional Standard
list-rate scenario**, assuming $0.20 per million input tokens and $1.25 per
million output tokens, and allowing 25% input cache-write and 10% regional
uplifts. [OpenAI's model page](https://developers.openai.com/api/docs/models/gpt-5.4-nano)
listed those rates on 27 September 2026. The guard is an upper scenario under
those assumptions, not a spending guarantee or verified invoice. Stop after
any provider/usage failure. Preserve raw response JSON, prompt hashes,
per-arm usage, elapsed time and the explicit paired score.

The freeze enumerates `argument.eal`, `cases.json`, `oracles.json` and
`run.py`. A change to any of them requires a new named pilot version and a
new freeze, never editing an observed result. CI always verifies the digest
before either offline or paid work. The original v4.0.1.4 freeze is separate.
