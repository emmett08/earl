# Order fulfilment architecture

The customer submits a purchase request containing distinct SKUs, whole-unit quantities, a delivery address and an opaque payment token. `CheckoutService` quotes each unit, reserves all stock, captures the full amount once, dispatches the reservation, then stores the order and its event in one order-store transaction. Flat inventory uses one warehouse (`main` by default); nested inventory may span warehouses. The immutable `Order` retains the quoted unit price and unit tax, stock allocations, captured charge, and shipments with their warehouse IDs and allocations. These records establish which units were paid for and where each unit came from.

`ports.py` defines pricing, inventory, payment, carrier, order storage and event delivery contracts. The application workflow depends on those contracts; `memory.py` provides deterministic adapters for the experiment. An adapter may replace a contract implementation, or a materially new requirement may justify revising a contract and every affected caller. A new feature must keep one coherent path for each side effect. In particular, all inventory changes must pass through the stock boundary, all financial changes through payment, and shipment operations through shipping. The application should use the same order and outbox model for any new order events.

The pricing adapter applies tax per unit with half-up rounding to a penny. A line's pre-tax amount and tax are the respective unit amounts multiplied by its quantity. The quote totals sum the line amounts. This gives a deterministic amount for each selected unit if a later requirement changes an order. The stock adapter plans the full demand before reducing any SKU. It accepts flat single-warehouse inventory or nested depot inventory with a priority tuple; each SKU is allocated in priority order across warehouses until satisfied. A reservation lists immutable `Allocation(sku, quantity, warehouse_id)` values in warehouse priority order. The carrier receives the reservation and creates one immutable shipment per contributing warehouse, grouping its allocated SKUs. The order event records the final allocations and shipments.

The request ID identifies a purchase. Repeating it with identical inputs returns the stored order and retries pending events; changing any customer, line, address or payment token rejects the key. The order store also fixes the request fingerprint after a failed attempt. Each attempt obtains a fresh operation key, so a fully refunded charge from one failed attempt cannot satisfy a later attempt. The in-memory implementation is sequential: concurrent requests and durable storage across processes are outside this fixture's current guarantees.

If capture, dispatch or order storage fails, the service reverses completed shipment, charge and reservation operations in that order. A failed compensation raises `CompensationFailure` with the original failure and the failed compensations for explicit reconciliation. The carrier raises `DispatchFailure` containing every shipment completed before a later warehouse fails; the service cancels those receipts. The in-memory carrier has a `fail_on_shipment_number` injection seam for testing this contract. Once the order and outbox event have been stored, event delivery failure does not undo the purchase. Pending events retain insertion order for later retry; the sink deduplicates event identifiers.

Run the baseline from this directory with `python -m unittest discover -s tests -v`. The in-memory adapters deliberately expose effects and injectable failures for reproducible assessment; they are not production persistence, payment or carrier integrations.

Partial returns use the original order's shipment allocations and quoted unit price and tax. The order store validates each return against shipped quantities and committed or pending returns, then holds the request ID and content before payment. The payment and stock ports use that request ID as an idempotency key; a retry after either the stock restoration or order-store commit fails cannot repeat a completed effect. The store commits the receipt, cumulative returned quantities, and return event together in its outbox. A failed payment leaves no committed return or inventory change. Event delivery uses the same retry path as checkout. An unresolved pending return retains its capacity until retried or reconciled; the in-memory fixture assumes sequential callers and adapters that honor their idempotency keys.
