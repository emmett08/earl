# Prospective B–D architecture-evolution development study

**Status: specified; no v3 outcome observed.** This protocol is informed by the
v2 15/15 tie and its exploratory refund-failure finding. It is a development
and feasibility study, not an independently replicated confirmation of a
technical-debt reduction. The `W` family probes a different architecture
pressure, but shares the same A source and test harness. A later claim about a
population of codebases requires independent systems and more assignment
units. The `freeze.py` manifest must be created before the first v3 coding
session; host, EAL source, bindings, this assessor, feature briefs and analysis
code are frozen together. An instrument change after seeing an output creates
a new protocol version and preserves the original record.

## Question and rival explanations

The bounded question is whether providing a current, defeasible EAL/2
argument and its deterministic MCP evidence view improves the subsequent
change sequence in a cross-cutting Python fulfilment service, compared with
ordinary repository materials and compared with an equally fresh plain
evidence summary. The source anchor is the exact v2 A snapshot; all arms share
its implemented split fulfilment. Consequently this study estimates no effect
of EAL on constructing A. The treatment is the **bundle** of formal argument,
per-episode source-bound evidence refresh and a concise precomputed MCP
packet, rather than the string `EAL/2` alone. The host may retrieve detailed
explanations for audit; coding agents have no interactive `explain` tool in
this pilot.

H1 predicts that the EAL/MCP condition preserves or coherently revises shared
payment, stock, shipping, order and outbox boundaries while lowering the work
to implement later requirements. H2 predicts comparable results from
visible source, tests, documentation and ordinary agent reasoning; an EAL
packet may repeat what is already available. H3 predicts that a current
machine-produced evidence summary supplies the useful information and the
argument formalism adds no material advantage. H4 predicts a cost or adverse
effect from extra context, stale evidence, overconstrained advice or faulty
assumptions. Passing the same tests in every arm is shared evidence compatible
with H1, H2 and H3; a favourable result alone cannot identify the agent's
internal reasoning mechanism.

The practical threshold, fixed before execution, is **at least 25% lower
restricted subsequent-change completion time** in P2 than in each comparator,
with every critical invariant passing and no lower verified-completion rate.
This time includes the current-stage host packet acquisition before C and D,
plus capped agent coding time; report the components and total B–D lifecycle
time separately. It excludes queue and independent post-run assessor time,
which are measured but do not form the agent's change path.
Priced model/tool expenditure is a separate cost outcome when provider usage
and rates are completely logged; a time result cannot be called a financial
saving.
The threshold is a decision criterion for this deliberately bounded system;
it is not a fact about EAL. A one-block-per-family pilot can record whether
that local pattern occurred. It cannot establish a population effect or a
precise confidence bound.

## Frozen task bank and experimental units

The [task bank](task-bank.json) contains `R` and `W`. Each begins from the
identical v2 A source. `R` has partial returns (B), cancellation of outstanding
shipped units (C), and refund acknowledgement reconciliation (D); its D
selection is partly motivated by v2's post-run diagnostic. `W` has warehouse
availability (B), carrier rejection and substitution (C), and bounded ordered
event delivery (D). The task family and its B–C–D order are fixed before
coding. The briefs specify required behaviour and testable public interfaces,
without naming an architecture, design pattern, source file to edit or an
argument conclusion. The host reveals only the current brief to an agent.

One independently cloned **entire B–C–D sequence** is an assignment unit. A
fresh coding agent receives the current clone, direct brief and its arm's
predeclared environment context at each episode. The resulting source is the
next episode's starting source within that sequence; this carry-over is the
phenomenon under study. Never count three episodes as three independent
replications. Initially run one three-arm block in each family, six clones and
eighteen planned coding sessions. One attempt per episode is retained,
including failures; no successful rerun substitutes for an assigned failure.
Independent subsequent blocks need a new versioned registration and the
sample-size analysis below.

The allocation file records a 256-bit random seed and a permutation of P0,
P1, P2 onto masked clone IDs for each family before coding starts. It does
not prescribe job start order; clones may run concurrently, while B→C→D
remains sequential within each clone. The seed and algorithm are auditable;
host packets may reveal the arm to the operator.
Assessor and architecture reviewers receive masked candidate IDs and source
without the arm packet. The B, C and D stages may use the same or different
agent classes/models as a **predeclared stage profile**, but model class,
exact model identifier/version when exposed, reasoning setting, tool
restrictions, wall cap and runner version match P0/P1/P2 within each family
and stage. A later profile is a separately reported block; never substitute
a model in one arm or pool class changes as treatment. Record the profile
and exact workflow inputs before jobs start. An unavailable backend revision
is marked unknown, not inferred from the requested label.

## Intervention and exposure contract

- **P0 ordinary:** the code, its existing architecture document and tests,
  ordinary coding tools, and the current feature brief. No EAL packet or
  special evidence summary is delivered.
- **P1 evidence comparator:** P0 plus a concise, current plain evidence
  packet containing the same raw source checks, effect-route counts, public
  feature impact facts, architectural guidance and selected verification
  choice as P2, from the same host collectors and packet budget. This is an optimised prose
  comparator, not a straw-man document dump.
- **P2 EAL/MCP:** P1's raw facts, guidance and verification choice, plus a
  concise EAL/2 argument packet with ASPIC+ attack/status structure, a claim
  status and selected decisive route identities. The source explicitly leaves
  sealed conformance and future debt unestablished. Its argument must
  re-evaluate against the **current** B, C or D snapshot; a pre-A baseline
  packet is stale and invalid for the episode.

The P2 host records a real MCP `tools/list`, `assess` and `finish` request/
response sequence. It retrieves full `explain` only on host audit demand;
explanation bytes are not an agent critical-path cost when no explanation is
requested. Record the exact request/response wire, tool and packet digests,
snapshot digest, stage, latency and errors, including failed or contested
collections. The host records
the exact precomputed packet actually offered to the agent and observed
file/tool access where the runner supplies it. The host-only `explain` route
is an audit affordance, not an agent-visible treatment. Delivery is a
manipulation check, not proof
of reading or following. In a clean run, the coding agent is mounted in a
separate workspace containing only its clone, current brief and assigned
packet; the EAL source is host-only for P0/P1, as are future briefs, assessor
and other candidates. A public PR with network-enabled coding agents still
permits retrieval of committed host-only materials; a fully concealed
confirmatory study needs unpublished materials and controlled egress. A shared
filesystem with full checkout supplies only an
instruction to avoid them, **not technical concealment**. Record mounts,
filesystem reachability and any read access; if isolation is unavailable,
describe a feasibility run with possible contamination, not a blinded test.
Tool access differences, agent-visible leakage, failed deliveries and source
mismatches are reported for **all** assigned attempts; the intention-to-treat
description remains, while a clean treatment-contrast claim is suspended.

The host spends tokens on the current high-value subargument, source change
and unresolved attacker, not a full graph. Agent-facing deterministic
collectors measure current source identity, changed files and bounded public
structure checks. They never run the independent hidden assessor or reveal
its failing probe IDs, cases or results. Candidate-visible tests, if used,
must be identical in P1/P2 and remain separate from sealed scoring. Raw
public collector records are retained for host audit. Record
collector CPU, network and token footprint so a concise packet is not called
cheap solely because its construction was hidden. The same enforceable wall
time cap applies across arms. A nominal token target is only advisory if the
agent action cannot enforce or attest it; report actual usage coverage rather
than silently calling it an equal hard budget.

## Independent outcomes and construct validity

The assessor is host-only. At B, C and D it reruns the earlier independent
probes plus the newly due cases. The `R` family retains v2's five baseline,
five A and five B checks and adds cancellation and refund ambiguity checks.
The `W` family retains the ten baseline/A checks and adds availability,
substitution and event-delivery checks. Fresh in-memory rigs isolate probes.
The tests cover deterministic, sequential behaviour and cannot establish
concurrency, durable crash recovery or provider behaviour beyond the declared
adapter. Assessor source digests bind every finding to the exact snapshot.
Hidden tests are not passed through the EAL collector or shown to coding
agents. A failure is `fail`; an import or assessor failure is `invalid`, not
evidence that the property is false.

The primary result is the ordered **verified-conformance vector** by episode,
including all earlier regressions and critical payment/inventory/event
invariants. A second decision outcome is the **restricted elapsed process time
to verified completion across C and D**, the prospective subsequent changes.
Give each arm the same predeclared 30-minute wall cap per episode. For an
episode that fails independent verification, assign the 30-minute cap to the
restricted-time decision measure, explicitly an unsuccessful/censored value,
not the actual elapsed time. Report actual elapsed time and failure separately.
The coding clock starts when the action begins and stops when its candidate
snapshot is sealed. Add the packet acquisition wall time measured by the
host before the current coding stage (zero for P0) to the restricted coding
time for the practical threshold. Queue and independent sealed-assessor time
are reported separately.
Also report host/child CPU, MCP elapsed time, delivered packet bytes and
internal tool-exchange bytes as separate components. MCP elapsed is contained
in host wall time, and CPU is a different resource measure; neither is added
again to process time or counted as agent tokens.
If the workflow cannot attest episode-level elapsed time and cap enforcement,
the 25% time decision cannot be made from that block. Record model input,
output and cache tokens, actual tool compute and human intervention from
timestamped ledgers where available, apply disclosed run-time prices with no
double counting, and mark financial cost missing when usage or rates are
incomplete. Functional completion is not inferred from agent tests or reports.
Retain agent-visible test failures and subsequent edits as an exploratory
rework trail only when the runner exposes those events with timestamps. A
completed task can contain no visible test repair while still fail the sealed
assessor. Because the sealed failures are never returned to the agents, this
pilot measures later change implementation and internal correction cycles,
not the labour required to remediate all hidden defects or a debt principal.

Two condition-masked reviewers independently apply a frozen architecture
rubric: independent mutation paths for one order/return/cancellation state,
port bypasses, incompatible outbox writers, duplicate maintenance sites,
reachable obsolete code, and fan-out of changed modules/call sites for the
same later requirement. They give source locations and a plausible alternative
reading. A third adjudicator records disagreement before labels are revealed.
Static counts are diagnostics, not effort or debt by definition. Cognitive
Complexity is reported per function and by changed/added/removed functions
post-run with the pinned v2 Python instrument; it never overrides a correctness failure or
proves debt reduction. Calibrated token spend, latency and independent review
are separate outcomes, not ingredients of an arbitrary score.

The attached language-agnostic debt model can supply a **secondary**
conditional valuation only after source-independent work observations exist.
Specify an attainable behaviour-equivalent reference `r`, common work demand
`lambda`, initial/induced work `M,B`, unit cost `c`, remediation plan `P`,
horizon `H` and discount `delta`. Its
`D_H = delta^H P + g_H(delta) J` requires stationary first moments,
subcritical induced work and a declared accounting convention. Direct paired
carrying cost is preferable to an unidentified propagation matrix. If the
reference or P is not observed, report a scenario or interval with unresolved
inputs rather than treating a static smell/complexity count as pounds of debt.
Do not add debt-model valuation to observed expenditure, since that would
double count maintenance work.

## Estimand, analysis and decisions

Let `i` index a family × exact-model/class block and `z` one of P0/P1/P2.
The finite pilot contrasts are
`Y_i(P2) - Y_i(P0)` and `Y_i(P2) - Y_i(P1)` for the fixed outcome vectors,
and corresponding differences in restricted C+D elapsed time. The first contrast
assesses the package against ordinary materials; the second asks whether
formal argument route/status delivery adds value beyond the same deterministic
evidence, substantive guidance and verification choice. It cannot isolate
ASPIC+ semantics from route naming, status presentation or packet length.
These are descriptive potential-outcome contrasts in a small deliberately
constructed task bank, with distinct stochastic agent sessions. Random clone
assignment does not eliminate run-level variation or justify generalisation.

Report every stage's exact probe vector, import/assessor status, source digest,
model/tool version, wall time, tokens and priced costs (when available), MCP
trace digest, masked architecture findings and per-function complexity.
Never condition the primary comparison on an agent having used MCP, a passing
earlier stage, successful review or a completed PR: these are post-assignment
selection variables. If an earlier stage fails, retain the branch and continue
the scheduled brief where safe; if a later feature is structurally impossible,
record the inability and the assigned cap/verification status. Do not give a
different task or hidden repair instruction to one arm.

| Observation in the pilot | Interpretation and next action |
| --- | --- |
| P2 passes all critical checks and has at least 25% lower restricted C+D elapsed time than both comparators in both families, with no worse masked structure | Substantial **local time** feasibility result; report priced expenditure separately and preregister independent systems before a general causal claim. |
| Same conformance and elapsed-time difference below threshold or mixed signs | The practical advantage is not demonstrated by this pilot; retain all vectors and task-family interactions. |
| P2 fails a critical invariant the comparator passes | Adverse local result; diagnose the exact argument premise and MCP/tool behaviour before revising it. |
| Every arm passes at similar elapsed time and spend | Ceiling/visible-code explanation remains live; no EAL benefit established on these changes. |
| All fail or assessor cannot execute | Task/apparatus feasibility problem; preserve failures, version any correction, and do not select only successful clones. |
| Packet missing, model mismatch, leaked future brief or hidden assessor, unequal source or unlogged elapsed time | Suspend the affected clean comparative claim; retain attempt and report the exact deviation. |

One block per family yields no defensible population p-value. A confirmatory
successor should sample independent systems/task sequences under an eligibility
rule fixed without looking at treatment outcomes, run several randomised
blocks per system, and simulate sample size for the observed within-system
variance, family clustering, censoring and a 25% meaningful threshold. It
should predeclare a randomisation-based interval or hierarchical estimator
and a correctness noninferiority margin justified by risk, not an arbitrary
number. Stop at the registered count regardless of signs; sequential stopping
requires its own alpha-spending or decision-utility rule. Pilot effect sizes
cannot be promoted to confirmation by analysing the same units again.

## Safeguards and execution record

Preserve deterministic source/brief/assessor/model/tool digests, allocation
seed and clone assignment, actual job start order, packet delivery traces, all attempts and outputs, hidden test
results, censored cost ledger, independent review forms and all deviations.
The v2 A snapshot and v2 assessor are external frozen dependencies explicitly
hashed in the manifest. Environment-sensitive prices are declared at block
start with dated source; unknown pricing produces separate token/compute units.
The host must never mutate a worktree after an episode's snapshot digest is
recorded. No v3 coding outcome, confirmatory study, debt valuation or
substantial treatment effect is claimed by this protocol alone.
An optional [local collaboration-agent feasibility exercise](LOCAL-FEASIBILITY.md)
uses a separate record and cannot adjudicate this workflow's 25% threshold.
