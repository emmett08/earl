# Feature A: split fulfilment

An order may be fulfilled from several warehouses. `InMemoryStock` must accept warehouse stock as `on_hand={warehouse_id: {sku: quantity}}` with `priorities=(warehouse_id, ...)` in addition to its existing single-warehouse input. Each warehouse has its own stock for each SKU. Allocate a requested SKU from warehouses in priority order, taking the available quantity at each until the requested quantity is met. A warehouse that contributes units produces one shipment containing all units allocated to it. Shipments and the order result must identify their warehouse and allocated SKU quantities.

For example, if `north` has two units, `south` has two units, and an order requests three units of the same SKU with priority `north`, then `south`, the order has a two-unit `north` shipment and a one-unit `south` shipment. Charge the quoted order total once regardless of the number of shipments. A request whose aggregate available stock is insufficient must leave stock, payment, shipment state and order history unchanged.

If dispatch at any warehouse fails after an earlier warehouse has dispatched, no shipment from that attempt may remain active. Restore reserved stock, refund the charge once and do not publish an order-placed event. A retry of the same successful request ID returns the original order without repeating external effects; reuse of that ID with different request content remains an error. Preserve the observable results for orders that use one warehouse. Emit the final order event with its actual allocations and shipments; transient event publication failures remain retryable without repeating fulfilment.
