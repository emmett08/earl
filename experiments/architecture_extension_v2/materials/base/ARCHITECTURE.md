# Baseline order fulfilment architecture

The customer submits a purchase request containing distinct SKUs, whole-unit quantities, a delivery address and an opaque payment token. `CheckoutService` quotes each unit, reserves all stock, captures the full amount, dispatches the reservation, then stores the order and its event in one order-store transaction. The baseline has one warehouse (`main`) and one shipment per order. The immutable `Order` retains the quoted unit price and unit tax, stock allocations, captured charge, and shipment allocations. These records establish which units were paid for and where each unit came from.

`ports.py` defines pricing, inventory, payment, carrier, order storage and event delivery contracts. The application workflow depends on those contracts; `memory.py` provides deterministic adapters for the experiment. An adapter may replace a contract implementation, or a materially new requirement may justify revising a contract and every affected caller. A new feature must keep one coherent path for each side effect. In particular, all inventory changes must pass through the stock boundary, all financial changes through payment, and shipment operations through shipping. The application should use the same order and outbox model for any new order events.

The pricing adapter applies tax per unit with half-up rounding to a penny. A line's pre-tax amount and tax are the respective unit amounts multiplied by its quantity. The quote totals sum the line amounts. This gives a deterministic amount for each selected unit if a later requirement changes an order. The stock adapter checks the full demand before reducing any SKU. It accepts flat single-warehouse inventory or nested depot inventory with an explicit priority tuple, but baseline reservation uses only the first depot. A reservation lists immutable `Allocation(sku, quantity, warehouse_id)` values. The carrier receives the reservation and returns immutable shipments whose allocations can be compared with reserved units.

The request ID identifies a purchase. Repeating it with identical inputs returns the stored order and retries pending events; changing any customer, line, address or payment token rejects the key. The order store also fixes the request fingerprint after a failed attempt. Each attempt obtains a fresh operation key, so a fully refunded charge from one failed attempt cannot satisfy a later attempt. The in-memory implementation is sequential: concurrent requests and durable storage across processes are outside this fixture's current guarantees.

If capture, dispatch or order storage fails, the service reverses completed shipment, charge and reservation operations in that order. A failed compensation raises `CompensationFailure` with the original failure and the failed compensations for explicit reconciliation. The current carrier dispatch is atomic for one shipment. The carrier contract permits either an atomic failure or a `DispatchFailure` containing every shipment completed before a later failure; the service cancels those receipts. The in-memory carrier has a `fail_on_shipment_number` injection seam for testing this contract across extensions. Once the order and outbox event have been stored, event delivery failure does not undo the purchase. Pending events retain insertion order for later retry; the sink deduplicates event identifiers.

Run the baseline from this directory with `python -m unittest discover -s tests -v`. The in-memory adapters deliberately expose effects and injectable failures for reproducible assessment; they are not production persistence, payment or carrier integrations.
