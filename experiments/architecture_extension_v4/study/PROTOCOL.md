## Question and scope

For the three included Python services and their specified B–C–D changes,
does an EAL/2 formal argument *presentation* change a coding agent's verified
implementation or its response to a defeated premise relative to the same
facts, statuses and action guidance in plain prose? P2 versus P1 is the
primary representation contrast. P2 versus P0 is a secondary whole-packet
contrast. Both renderers use the same source-derived decision content; this
experiment cannot isolate EAL's inference algorithm from an alternative
algorithm, measure the language's intrinsic value, or establish a general
technical-debt effect.

Fulfilment is the exact previously observed v2 A source and v3 R briefs,
with the corrected v4 assessor. It is a development/calibration stratum.
Entitlement and reservation are two newly constructed, separate service
fixtures. They are purposively chosen and authored within this project,
not a random sample of production codebases. Report each system separately;
even three favourable systems cannot license a population-wide claim. The
source anchors, current-stage briefs and host-only assessors are in
`systems/{fulfilment,entitlement,reservation}`. Agents receive only `source/`
and the current stage's `features/{B,C,D}.md`, not host controls or future
briefs. All fixtures are offline and use Python's standard library.

The falsifiable rivals are that explicit information is sufficient (P1 and
P2 behave alike), that formal presentation helps the agent retract an
attacked inference (P2 alone changes correctly), or that additional
structure costs time and tokens or prompts unwarranted deference. A failure
in shared collector or assessor discriminates none of these.

## Units, allocation and execution

One independently cloned entire B→C→D lineage is the assigned unit; later
source in that lineage inherits earlier changes. A system × replicate block
is a matched triad of P0/P1/P2 lineages allocated by the new frozen seed
in `manifest.json`. Within each system, the three triads use one of two
randomly selected cyclic orientation sets and a randomised block order. Thus
each arm runs once in each execution position within that system. This
restricted randomisation has 12 allowed schedules per system. Three blocks
per system create 27 newly assigned
lineages and 81 intended coding episodes. After D, each lineage receives two
fresh, 120-second, read-only decision sessions on frozen clean and defeated
finite-state cases, for 54 additional probe sessions. Their source and facts
come from registered host case fixtures rather than the agent's D candidate.
The probe never changes or feeds back into the B→C→D source. A strict choice
among frozen actions tests a decision change; transcript, validity, timing
and usage are retained separately from coding. Stages and sealed checks are repeated
measurements, not independent samples. All 0.1.4 assignments enter intention-to-
treat tabulation, including agent error, timeout, inaccessible model,
non-delivery, assessor invalidity and missing artifact. The partial 0.1.3
ledger remains a separate descriptive record: preserve successful episodes,
failed invocations, stopped blocks and uninvoked stages/probes as missing.
No 0.1.3 result is spliced into a 0.1.4 lineage. No successful retry replaces
the first assigned attempt within either version; a restarted workflow has a
distinct attempt identifier and is a protocol deviation unless it merely
recovers a host artifact without another coding invocation.

The same requested `gpt-6-sol` model, medium effort, Codex CLI `0.154.0`,
30-minute per-episode cap, prompt template, tool permissions and visible
source apply within each block. Record actual CLI version and requested model;
the provider's undisclosed backend revision is unknown. Run blocks concurrently
where possible, but B→C→D sequentially per clone. A coding process gets a
fresh home/session and a filesystem mount containing only its trial, read-only
system utilities and the provider network path. The outer mount is the sole
filesystem sandbox; within it Codex runs with `--sandbox danger-full-access`
to avoid attempting a prohibited nested namespace. The read-only decision
source is enforced by the outer read-only bind. Both mount modes and CLI startup
are checked without a credential before any live calls. The 0.1.2 preflight
also checks the effective DNS/proxy/TLS route inside each mount using a
credential-free provider request; only a symlinked resolver target file under
`/run` may be added to the read-only host view. Trial write checks use a fresh
exclusive probe name, preserving candidate bytes. The agent cannot see another
clone, assessor, later brief or host packet assembly. Host-only baseline
source checks run before the clone begins. Preflight failure is captured, not
promoted into a coding outcome.

## Intervention and proposition parity

P0 sees the current source and brief. P1 additionally sees a fresh plain
packet; P2 sees the same semantic content rendered as a formal EAL/2 argument
with attack and conclusion structure. For each candidate snapshot, the host
records a source-tree SHA-256, structural observations and collection errors.
It constructs one canonical content object containing facts, uncertainty,
counter-premise, conclusion status, selected action and guidance. P1 states
every proposition and defeater in sentences; P2 adds machine-evaluated EAL/2
identifiers and ASPIC+ statuses. Neither arm receives an extra recommendation.
The `shared_material_digest` must match on a same-snapshot parity probe, and
the rendered packets must be inspected proposition by proposition before
the first model call. Source differences arising after B are part of the
treatment sequence, so equality is checked on a common A snapshot and
within a packet's common content, not demanded between diverged later clones.
Record exact packet bytes, digest, acquisition wall time and the source digest
in its delivered trial. If parity or freshness fails, retain assignment but
withhold a clean representation-effect claim for that episode/block.

Source inspection is intentionally narrow. A syntactic fact about a method
or an `append` preceding a timeout raises a defeater against an unsafe
blanket inference; it does not prove all executions or production integration.
The frozen clean/contested pairs must change the action oracle in both
renderers. At D, fulfilment's unknown refund status forbids assuming
completion or retrying a new key, entitlement's issuer can append a token
before losing the acknowledgement, and reservation's historical bundle
receipt does not establish current availability after a move. The hidden
assessors separately test both admissible success and unsafe branches,
including replay/recovery and absence of duplicate external effects. An
agent's stated choice on the frozen case and its executable behaviour on its
own candidate are distinct outcomes. The case prompt withholds the oracle
from every arm, while P1 and P2 receive identical facts, uncertainty and
general guidance. The case sources are construction/measurement apparatus,
not new independently sampled coding systems.

## Measurement and analysis

Per-stage sealed output is an ordered vector of `pass`, `fail` or `invalid`
checks, retaining the candidate and assessor digests. Passing all due checks
defines verified completion within this fixture; a visible test, agent claim
or packet decision does not. Prespecified critical checks are the no-duplicate
effect, atomicity, current-state validation and conflict/retry checks named in
the assessor. Publish individual cases, not merely a total. Host exceptions
and missing assessments are invalid/unknown, never pass. Report assigned
lineages passing B, C, D cumulatively and the contested-action pair outcomes.

Two reviewers independently receive masked candidate source, A baseline,
current brief and a system-specific rubric. They receive no arm packet,
transcript or sealed behavioural score until both forms are locked. A third
reviewer adjudicates disagreements without erasing originals. The rubric
requires anchored file/line evidence for shared transition, effect ports,
event/outbox path, duplicated maintenance, obsolete reachable code and
propagation surface, with severity and reviewer confidence. Record broken
masking and missing reviewers. Automated source counts may aid description
but cannot substitute for the requested masked architecture findings.

Time is monotonic actual coding wall time, capped at 1800 seconds; record
host packet preparation, queue and independent assessor time separately.
The prespecified failure-penalised *decision score* for an episode is actual
time capped at 1800 if all due checks pass, otherwise 1800. Sum C+D scores
and acquisition time per lineage. This is a penalty convention, not measured
repair time. Always show actual elapsed and failure counts beside it. The old
v3 threshold of 25% lower C+D time versus each comparator is a practical
criterion only if completion is no worse and masked critical architecture
findings are no worse. With three systems, point estimates alone cannot
establish that threshold; no unearned significance test or population CI.

Usage records preserve raw per-request/turn token classes, cache fields,
model, request ID, tariff tier, region, context length and billing channel.
Zero means reported zero; absent means unknown. `price.py` may compute a
labelled public-list-price amount only if complete request-level API-key
records match `rate-card.json`. Subscription credits, unknown cache-write
quantities, unverified region/tier or turn aggregates have no exact USD total.
Invoice reconciliation remains separate. Provider, collector and runner
resources are separate; overlapping wall clocks are never summed as spend.
Report resource vectors even when the money field remains unresolved.
As an operational stop, each nine-episode/six-probe block has a **USD 15.00
upper conditional Standard-list-rate scenario cap**. The runner checks the
sum after each invocation and stops that block if input/output usage cannot
be bounded or the cumulative high scenario exceeds the cap. A missing
cache-write partition remains unknown and is assigned the dearer eligible
input rate in this conditional high scenario. Nine blocks
therefore have at most USD 135.00 in this scenario if every block completes.
The cap is not an invoice or guaranteed monetary ceiling: an individual call
may cross it before its tokens are observed, and a different account tariff,
tier or credits alter actual charges. This choice is based on a replay of 18
v3 CLI episodes whose corresponding high scenario summed to USD 7.17, with
maximum USD 0.64 per coding episode. It is an operational guard, not evidence
of a v4 effect.

For each scalar lineage outcome `Y`, the included-system estimand is the
equally system-weighted mean of within-block differences:

`Δ(P2,P1) = (1/3) Σ_s (1/3) Σ_b [Y(s,b,P2) − Y(s,b,P1)]`.

Report raw matched differences and each system separately. Missing outcomes
stay missing with explicit bounds/sensitivity; no complete-case result is
promoted without attrition disclosure. For any randomisation inference,
enumerate only the 12 allowed position-balanced schedules per system, not
independent permutations within triads. The 0.1.3 partial cohort is displayed
separately and never pooled into the 0.1.4 primary estimator. Assignment is
random within the registered restricted design, but systems and tasks are
purposively selected. No population-of-software inference follows.

## Decision rules and stops

If P2 alone chooses the correct defeated action, passes sealed cases, and
masked critical findings are no worse, this supports a local representation
advantage in those recorded decisions. If P1 and P2 both change correctly,
information suffices for that decision. If P2 is faster but worse on critical
behaviour or architecture, report the adverse trade-off. A ceiling, mixed
systems, unchanged action or invalid measurement leaves the comparison
unresolved. Cost is unpriced when required usage or rate identity is absent.
The finite results cannot prove EAL/2 reduces future maintenance debt.

A validation failure before live acquisition stops the run. The 0.1.4
workflow draws its process `CODEX_API_KEY` from the distinct repository secret
`CODEX_API_KEY`; this credential source and its billing identity are recorded
as a post-0.1.3 amendment. One isolated Responses API request with an output
cap verifies immediate model entitlement before parallel live jobs. It does
not verify the pinned Codex CLI's authenticated integration or guarantee
sufficient credit for the full wave. It is outside the coding and decision
units; its allowlisted token usage and elapsed time are reported separately. During
live acquisition, preserve completed and failed assignments, state the exact
stopping cause (credential, budget, infrastructure, isolation or other) and
do not silently change the credential, model, assessor or cap. The workflow may use a
bounded concurrency setting; actual billed expenditure cannot be enforced
from CLI turn aggregates and must be reported as unavailable until reconciled.
Publish
the freeze manifest, assignment ledger, raw episode records and analysis
code with results, retaining provider secrets only in the action environment.
