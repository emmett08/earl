# Executable argument host

EAL/2 describes a bounded argument. The argument host connects an incoming claim, decision question or proposed action to a reviewed EAL/2 argument form, runs its configured evidence tools, evaluates the argument and assesses whether the evidence meets the additional requirements for the intended conclusion. It operates before an optional language-model response. The model can supply a candidate reading of unfamiliar prose, but that candidate does not select host executables or certify its own correspondence with the request.

The host has four separate responsibilities. A recogniser proposes a form and typed bindings from the current text and host context. The EAL/2 runtime validates the instantiated source, collects observations and runs the declared methods and objection calculus. An adequacy evaluator checks the claim-to-source correspondence and evidence obligations attached to the reviewed form. A result renderer returns the checked state with its assessment identity and unresolved obligations. Host-installed TOML configures the forms and executable tools; input prose never supplies command paths or changes the method registry.

The recognised form is an argument procedure, rather than a stored conclusion. A later request can reuse it with another admissible subject or a fresh observation. Reuse requires fresh binding and assessment at the decision time. The observation store retains provenance and historical conclusions, while the session record retains the host's selected form and validated context. A previous status is never treated as current solely because its source, task or wording looks similar.

## Correspondence and sufficiency

Three relations are checked separately. Where a formal proposition is present, it must address the selected subject, quantity, unit, scope, query and result criterion. A reviewed source contract records the intended relationship between the exact written statement and the EAL claim; its review remains a human assertion about meaning. A separately delivered model sentence or novel input paraphrase needs its own correspondence route. The executor cannot establish arbitrary English equivalence from a digest, tool result or parsed formula.

An observation may be authentic and fresh yet insufficient. A load test with 100 requests and no failures meets a descriptive zero-failure condition but does not, without sampling assumptions and an uncertainty calculation, establish a population failure probability below one per cent. An adequacy contract declares the target conclusion, required evidence identities and method outputs, assumptions about sampling and coverage, and any outstanding objections. A failed requirement yields `insufficient`; a missing or semantically unchecked requirement yields `unresolved`. An `adequate` result means the declared, reviewed requirements have been met for that source, context and assessment time. It does not establish that the author selected every material requirement or that the external measurement was genuine. For formal deduction, each formula used as a premise must have an explicit `premise_bindings` entry connecting it to a supported named EAL claim. Clauses about assumptions and objections require an `about` relation and must address those declarations' own supporting evidence.

For a file change, the proposed bytes and existing file identity are part of the question. The guarded editing path evaluates the proposed change through its configured preflight procedure and commits only when the checked action assessment and adequacy requirements hold for the same proposal and unchanged baseline. Project-specific design and integration constraints need executable checks or reviewed arguments whose observations are collected against that proposed change. A generic model statement that the change is consistent is not such an observation. `StagedCommandValidator` runs trusted, versioned command vectors over a temporary staged candidate and selected project inputs. It requires SHA-256 pins for the checker executable and every absolute script/dependency argument, checking those bytes at preflight and commit. The staged location is not a process sandbox. The supplied gate covers one existing regular file at a time. It cannot stop another writer outside the gate or certify constraints absent from the installed checks.

## Result states

The EAL/2 `supported`, `contested`, `unsupported` and `out_of_scope` labels retain their existing meaning for the authored argument. The host also reports applicability and adequacy. It may deliver the scoped conclusion as supported only when the form is uniquely applicable, the checked EAL/2 claim is supported and adequacy is `adequate`. It reports disagreement, missing information and out-of-scope questions explicitly. Missing support is not evidence for the opposite claim. The host can render a checked factual answer before calling a model; model prose remains separate and cannot overwrite the assessment fields.

## Scope of automatic reuse

Reviewed surface forms with typed slots can resolve a range of later phrasings and subjects. A model or another recogniser may propose a form for a previously unseen wording. The host checks the proposed identities, slot types, scope and correspondence through an independent validator; an unverifiable interpretation stays unresolved and does not run evidence tools. This is an extensible recogniser boundary, not a universal natural-language equivalence algorithm. A deployment that needs wider automatic coverage must test its recogniser and validator on representative paraphrases, changed subjects, negation, compound requests and adversarial wording.

The current EAL/2 methods remain bounded. `structured/1` evaluates authored dependencies and does not prove its prose rationale. Formal deduction checks its implemented propositional fragment; statistical and causal outputs retain their stated assumptions. New reasoning procedures belong behind typed, versioned method contracts. Reusing a checked status or a code-change approval after source, method, observation, context, proposal or baseline changes requires a new assessment.

## Integration contracts

The host keeps the compiler-like pipeline in separate components. `ArgumentRecogniser` proposes a scheme and typed slots, while `CorrespondenceValidator` independently checks a novel interpretation. `ArgumentHost` verifies pinned EAL source and selectors, resolves the reviewed form, executes its claim closure through `ReasoningService`, calls `AdequacyEvaluator`, and persists an immutable answer packet. Finalisation checks the current selected tool-binding configuration against the collected records; this identifies registry changes, not changes to the executable's bytes or external data. `ActionGate` consumes only a checked action packet and a `ChangeValidator` result. These are injectable interfaces: a deployment can install a domain recogniser, semantic reviewer, method registry, collector and staged file checks without giving the model authority to define executables or approve its own output.

The trusted launcher can expose the procedures to a recipient model using `eal-mcp --schemes SCHEMES.toml --registry TOOLS.toml --recipient-only --recipient-principal USER --session-id SESSION --scheme-grant SCHEME --bound-prose-file REQUEST.txt`. It supplies the original request from `REQUEST.txt` and the grant; the model calls the no-argument `eal_resolve_bound_prose` or `eal_assess_bound_prose`, then `eal_finish_prose` with the issued assessment ID. The recipient cannot replace the text, source, context or form with its own arguments. An operator endpoint may supply prose, context and a role candidate explicitly. `eal-argument-host` provides an operator CLI for direct assessment. A later prompt is resolved again against reviewed forms and fresh evidence, including after a service restart when the same principal and session store are available.

A scheme catalogue uses `schema = "eal2-argument-schemes/1"` and `[schemes.NAME]` entries with `source`, `source_sha256`, `claim`, `kind` and `forms`; it can add `followups`, `context`, `parameters` and an inline `adequacy` contract. The host derives its exact instantiated source/claim/method identities rather than accepting those from the incoming request. An obligation compares a scalar field of a named evidence record, argument computation, assumption, objection, claim or context. For example, a reviewed statistical criterion can require an accepted `inductive/1` result's `reasoning_result.details.upper <= 0.01`, while a separate clause checks sample size and another checks subject identity. A method result or a successful executable by itself is insufficient. The [maintained load-test example](../examples/api-load-test/README.md) supplies runnable configuration.

## Verification and evaluation

Use an independently checked task set to distinguish correct supported decisions, correct unresolved decisions, false support and failed completions. Include unrecognised paraphrases, misleading method output, wrong subject, stale evidence, failed collectors, incomplete sampling, objections and changed files between assessment and application. Compare the host with an equally provisioned ordinary validator and a model-only route under the same evidence access and answer contract. Measure collection/solver cost, latency and correctness together. The earlier four-case pilot tests a narrower checked-result distinction; it does not demonstrate general speed or superiority of this new host.
