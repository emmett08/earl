# GitHub Actions decision study

**Protocol:** `INV-EAL-CI-001`, version `0.1.0`. **Status:** `specified_not_ready`. No model snapshot, independently reviewed case, signed execution receipt or measured outcome has been enrolled under this version. [plan.json](plan.json) is the machine-readable specification; the four frozen candidate instructions are in [arms](arms/). A new version must be frozen before confirmatory calls.

## Question and example task

Does assignment to an EAL/2 argument **with the EAL MCP server** increase the probability of a correct, evidence-supported and faithfully communicated GitHub Actions release decision relative to a strong prose prompt, at the same named model, case, decision time, read-only evidence access and resource limit? The primary contrast is the complete assigned workflow, including choosing the relevant argument, authoring it, collecting records and explaining the checked result. Syntax alone and the MCP server alone are different questions.

The common natural request for the worked case is:

> Before releasing commit `{commit_sha}` in `{repository}` at `{decision_cut}`, determine whether the required `test` GitHub Actions workflow on **that exact commit** completed successfully and whether each job required by the release rule effective at the cut passed in the relevant run attempt. Read the workflow and release rule at the pinned commit and the permitted CI run, attempt and job records. Recommend **proceed**, **wait** or **investigate**. State the run and attempt identifiers, exact commit, required jobs, decisive records, relevant contrary records and any limitation. If the available record cannot justify proceeding, say so.

The case manifest supplies the repository and full commit SHA, rule and workflow paths, decision cut, bounded query, permitted tool catalogue and an opaque reference ID. It does **not** supply a selected argument, EAL source, graph, gold status or reviewer conclusion. The worked example can exercise a successful exact-SHA run, a success from another commit, a later failed attempt, a skipped mandatory job, a pending run, or an unavailable CI response. These are candidate case types, **not observations**. Review a real decision-time record independently before adding any case to the study. A fixture used to test the software is never a confirmatory case.

For the example, the permitted read-only operations are a pinned Git object read of the workflow and release rule, plus an authenticated CI GET of runs, attempts and jobs whose response identifies a source snapshot and observation time. The reviewed `tools.toml` command bindings serve the same exact, case-allowlisted inputs to P/T through the runner's acquisition gateway and E/J through MCP `eal_collect`. The ledger retains each request, tool/version, source identity, timing, result or error and digests. A retrospective CI adapter must read a historical snapshot whose information existed by the cut; a live GitHub API query cannot reconstruct an earlier decision merely by filtering the current response. The application uses least-privilege credentials and prohibits writes, workflow dispatches, approvals and deployment. The model cannot select executable paths or credentials. A live-only example collector does not make retrospective replay ready.

## Interventions and mechanism checks

Every arm sees the same common task, scope, decision cut and exact-input tool catalogue in a fresh session. E/J also receive the MCP-discovered language contract; J receives its typed JSON declaration contract. The runner sends **two model requests per arm** under the same ceiling. On the first, P/T select `{"calls":[...]}` while E authors `{"source":"...","claim":"..."}` and J authors `{"program":{...},"claim":"..."}`. The host executes the authorised calls or validates and checks the source over MCP. On the second, all arms receive their own records and give a final recommendation, explanation and cited record IDs. P/T state a model-chosen status; the application displays the host-owned checked status for E/J, retaining contradictory model prose for scoring. The linked files contain the exact arm instructions; the runner appends the phase-specific output contract.

| Arm | Assigned workflow | Inferential role |
| --- | --- | --- |
| [P](arms/P.md) | Strong plain prose request, evidence tools, no argument checker | Primary practical comparator. |
| [T](arms/T.md) | Six one-line Toulmin fields in prose, same tools | Tests whether explicit argument prompting suffices. |
| [J](arms/J.md) | Model-authored, meaning-equivalent JSON form of EAL/2, translated without invention into the same typed EAL/2 backend and checked through the same MCP server | Tests whether the EAL/2 textual notation affects authoring when checking and transport are held fixed. |
| [E](arms/E.md) | Model-selected/authored EAL/2, actual MCP stdio session, validation, collection, assessment and explanation, host-owned final status | Complete EAL/2 plus MCP intervention. |

E and J must exercise **the actual MCP transport and advertised schemas**, including `eal_validate`, `eal_collect`, `eal_reason` and `eal_explain`. Calling `ReasoningService` directly does not instantiate this intervention. J uses the versioned `eal2-ci-json-frontend/1` form of EAL/2's **direct declarations**; its host converts those declarations to EAL/2 **without filling missing arguments or evidence** and sends them through the same server. Patterns and applications are excluded from *both* E and J in this study version. Test parse–format–parse identity, JSON→source→IR meaning and equal results on valid, invalid, stale, wrong-commit, missing, cyclic and objection cases before claiming semantic parity within this subset. Record each MCP request, response, tool schema/version, assessment identity and failure. The host, not the model, calls MCP after the first authoring response; `eal_collect` uses the reviewed registry and records original source and observation identity.

Version 1 implements `selected_acquisition`: each arm chooses authorised calls from the same bounded catalogue and tools execute within that arm. This is the **primary end-to-end** comparison. A later `fixed_capture` diagnostic would execute tools once and deliver identical immutable traces to all four arms; it is **planned, not implemented** and would have a separate estimand. Do not pool the modes. Invalid source or JSON, irrelevant family, incomplete acquisition, failed tool or MCP call, budget exhaustion, refusal and inaccurate prose remain failures of their assigned attempts.

## Cases, models and reference

Start with a 12–20-family feasibility pilot. For confirmation, sample previously unseen and independently reviewed case families from genuine CI/release decisions. Group variants, repeated attempts, shared workflow/rule lineages and episodes of one incident in the same family; keep pilot and any exposed derivatives out of the holdout. Enrol both supported and adverse/indeterminate decisions, with the target mixture and any enrichment weights fixed from an eligible-case ledger. Include wrong SHA, outdated attempt, missing or cancelled required job, changed rule, conflicting records and access failures where they occur in genuine eligible cases. Retrospective replay and later read-only shadow cases have separate estimates.

Two engineers masked to arm and model independently record the decision-time status, exact query, admissible records, required jobs, contrary evidence, permissible action and uncertainty. A third resolves disputes with a retained rationale; an unresolved case may have an indeterminate reference. A provenance reviewer validates the source and time cut. Report pre-adjudication disagreement. The host's own label cannot define the reference.

Freeze a **named snapshot matrix** before confirmation. The target is at least eight snapshots from at least three independent model families or providers, including at least two small and two large models with published active parameter counts; declare size boundaries and the source of each count at freeze. Include at least two reasoning-optimised and two general instruction snapshots in each size stratum if available, plus hosted models of undisclosed size in a separate reported stratum. Do not infer a closed model's size from its price, name or performance. Pin resolved revision, provider/endpoint, sampling and reasoning settings, tool-interface adapter and pricing. If the target cannot be met, narrow the reported strata. Native tool calling is normalised through the same host request contract or analysed separately; it must not give one arm extra access.

The statement **“superior for all model classes” is universal** and cannot be established by any finite matrix. The confirmatory claim is confined to enrolled named snapshots and the prespecified, represented strata. A stratum claim requires a simultaneous interval above the frozen practical-gain margin for *each* prespecified stratum, with its false-support and coverage gates met; a pooled gain alone does not support it. Model-specific effects and heterogeneity are reported even if a pooled estimate is favourable. New model architectures, versions, providers and task families require replication.

## Assignment, outcome and analysis

Cross each case with each frozen model and P/T/J/E. Randomise and counterbalance arm order within case × model blocks. Use fresh contexts, no cross-arm memory, identical information horizons and prespecified upper limits for two model calls, output tokens, wall time, tool calls and money. Reserve a durable start for every arm before any call; normal completion adds one terminal outcome, while a crash leaves an interrupted assignment that stays in the denominator. Record every attempted model, registry and MCP operation. The current runner has no provider/tool retry; any later retry rule needs a new frozen protocol, retained prior failures and total cost. Provider outages are outcomes or declared protocol deviations under the frozen rule, never silent replacement. Actual tokens, human effort, latency and money are measured rather than assumed equal.

`Y=1` only when the assigned attempt selects a relevant claim and argument family, obtains admissible exact-commit decision-time evidence, applies the rule and query correctly, makes the independently permissible recommendation, and communicates the decisive grounds, material objection and qualification accurately. All required components are prespecified per case. Justified abstention can pass when the independent reference requires it; refusing an adequately supported case fails. Two masked scorers assess grounds and explanation; report their disagreement and adjudication.

`F=1` is an affirmative **proceed** when the independent bounded reference does not justify it. Use **all assigned adverse/indeterminate attempts** as the safety denominator, including malformed and absent outputs. Report actionable-decision coverage among cases with an adequate basis. Keep the raw model answer and displayed host status separate: enforcement can prevent status substitution while the model still miscommunicates the result.

The primary intention-to-treat estimand is the case-family-weighted paired risk difference `E[Y(E)-Y(P)]` over the frozen case mixture and equally weighted named models, for `selected_acquisition` retrospective cases. The false-support difference and minimum actionable coverage are co-gates. Report `E-T`, `E-J` and prospective shadow contrasts separately, plus cost per correct decision; add fixed-capture only after its separate runner implementation and freeze. Estimate paired differences by named model and prespecified size/reasoning strata; use uncertainty that resamples independent case families while retaining within-family attempts. Freeze practical improvement, maximum excess false support, minimum coverage, multiplicity, sample-size simulation, exclusion and stopping rules **after the pilot and before any confirmatory outputs**. A non-significant difference is inconclusive, not equivalence. An E–J authoring interpretation requires reviewed meaning-equivalent JSON conversion for the direct-declaration subset and identical MCP operations.

## Execution gate and status

The versioned runner and its one-attempt ledger require external signed case, independent-reference, tool-isolation, arm-parity, model-snapshot, sample/analysis, frozen-schedule and operational-stop receipts before a real study stage. The signature authenticates submitted bytes and reviewer roles; it does not establish that the factual judgement was sound. Do not promote the plan while receipts or margins are null. A local worked example or runner fixture needs no signed study receipt; it establishes software behaviour only and is labelled `simulated_fixture`.

Order: (1) review actual cases and execute each read-only adapter in a pilot; (2) freeze and register prompts, cases, models, grants, thresholds and analysis; (3) run held-out retrospective tool execution; (4) replicate as a later read-only operational shadow. No experimental arm controls production actions. Report observed failures, exclusions, raw and host-owned outputs, exact tool/MCP traces, adjudicator disagreements, actual cost, effect estimates and uncertainty. The current study stops at **specified, not ready**.
