# Prospective comparison of EAL/2 and prose in real engineering workflows

**Study ID:** `INV-EAL-REAL-001`  
**Protocol status:** `specified_not_ready`; no cases enrolled, calls made, results observed or confirmatory claims registered under this protocol.  
**Scope:** engineering decisions about a named claim at a particular assessment time, with access to actual read-only repository, CI, monitoring or infrastructure tools.  
**Relationship to earlier studies:** this is a separate study. The exposed synthetic cohorts, including `cross-model-confirmatory.json` and its `developmental_unreviewed` manifest, are development material and cannot enter the confirmatory holdout. The historical EAL/2 studies do not supply independent field references, complete effort accounting or prospective operational outcomes for this study.

**Implementation note:** [`runner_v1.py`](runner_v1.py) implements the four-arm orchestration and [`gateway_v1.py`](gateway_v1.py) executes pinned local Git object reads and allowlisted HTTPS JSON GETs. Signed case, tool, parity and model manifests plus a new ready execution plan are mandatory before real stages. This repository contains none of those externally reviewed materials or study outcomes. The gateway records decision-time and response identity but does not by itself prove historical snapshot immutability, network isolation, source authenticity or semantic parity between the EAL/2 and generic checkers; these need operator isolation, external review and retained receipts.

## 1. Question and competing explanations

For eligible engineering decisions, does assigning an agent the complete EAL/2 workflow improve the probability of a correct, evidence-supported, bounded and faithfully communicated recommendation, compared with a strong plain-prose workflow given the same question, evidence access and resource limits?

The primary claim is a **causal, workflow-level** difference for the selected case population, models, tool adapters, budgets and dates. It includes choosing a relevant argument family, authoring source, acquiring and validating evidence, executing checks and explaining the checked result. A checker may enforce a final status without making the source, warrant or physical record true. A result on an isolated parser or preauthored source cannot answer this question.

The rival explanations are: (a) explicit argument structure suffices without EAL/2; (b) a generic checked representation performs as well as EAL/2; (c) host control prevents status substitution while source and explanation failures negate an end-to-end benefit; and (d) any observed effect is confined to particular models, domains, evidence conditions or budgets. Accordingly, any advantage of EAL/2 syntax **specifically** requires a separate meaning-equivalent front-end comparison using the same typed semantic backend; the independent generic checker arm alone cannot identify a syntax effect.

## 2. Ordered stages and promotion gates

1. **Pilot and measurement calibration.** Assemble 12–20 independent case families spanning each intended case class and each tool adapter. Run all primary arms and available model snapshots with fresh contexts. Test reference adjudication, factual parity between arm briefs, adapter access, executable tool logging, scoring reliability, prompt/output contracts, budget feasibility and case-family dependence. Pilot cases and their derivatives are permanently excluded from confirmation. Amend the procedure openly where needed; retain failed attempts. A successful pilot permits a freeze, not an efficacy claim.
2. **Freeze the confirmation study.** Before any confirmatory model output is inspected, commit and hash the eligibility and sampling rules, case-family partition, real-case manifest and protected reference, prompts, source/checker versions, allowed tool contracts, model snapshots and inference settings, randomisation, retry policy, budget, rubric, analysis code, multiplicity, decision thresholds, sample-size simulation and stop rules. Register the freeze immutably, obtain required data/security review, and resolve all blocked adjudications. A nominal `confirmatory` configuration without these materials remains `specified_not_ready`.
3. **Held-out retrospective replay with executed tools.** Enrol real incidents, changes and operating decisions that occurred before the freeze but were not used in development or prompt tuning. Restrict each replay to facts available at its historical assessment time. Execute read-only tool queries against versioned historical repository/CI/log/metric snapshots and, where appropriate, isolated test runners. Preserve command, arguments, identity, exit state, timestamps, returned record and digest. A canned fixture delivered as if a tool had run is not an executed-tool case. Analyse this stage on its own target population.
4. **Prospective operational shadow.** Enrol new eligible decisions as they arise after the freeze. Execute the same read-only tools against live authorised systems; collect each arm's recommendation privately. The human operator follows the normal decision process without seeing experimental recommendations until the decision is recorded. No experimental arm may approve, write to or trigger production. Independent adjudicators review the information available at the recorded assessment time; a later outcome may inform a separately named follow-up endpoint, never silently replace that reference. Report the prospective estimate separately. A subsequent intervention trial of actual engineering actions would need a new safety and authorisation protocol.

If an adapter, reviewer, case count or security authorisation is unavailable, record the stage as blocked or exploratory. Do not fill missing field cases with synthetic variants and call the result field evidence.

## 3. Cases, reference and units

An eligible case is a genuine engineering question attached to a named system, claim, decision time and bounded evidence horizon, with at least one permitted tool path. The sampling frame should include release provenance, CI/test results, service incidents, metric/alert interpretation and infrastructure or deployment decisions across independent repositories or teams. Record all eligible cases and reasons for exclusion before model calls. Sample across straightforward support, unsupported or unavailable evidence, live objections, stale/conflicting records, wrong source or version, irrelevant candidate families and out-of-scope conditions. Enrichment for rare failures is allowed only with prespecified target-population weights; provide unweighted stratum results as well.

The **case family** groups variants or episodes sharing a system, decision template, underlying event, code lineage or evidence source. Split by family and time so transformations of an exposed incident cannot enter the holdout. The assignment unit is a case × named model snapshot × arm × repetition. The analysis unit is the assigned end-to-end attempt, with dependence at least by case family and model. Repeated prompts, multiple status revisions and tool calls are not independent engineering cases.

For every case, preserve a protected manifest with the question, claim scope and formal query, assessment time, source and tool permissions, relevant candidate families, evidence available at that time, reference provenance, admissible statuses, and any unresolved uncertainty. A neutral natural-language case brief is the common starting input. Do not hand the EAL/2 arm a preselected correct source, family, argument, host packet or checked status for the primary contrast. Independently review and hash the arm-specific renderings for equal factual content; arm instructions may differ only as specified below.

Two independent domain reviewers, masked to arm and model, first assess the case at the original decision time using permitted evidence. They record whether the proposed engineering claim has adequate support **within its stated scope**, the decisive records and query, known counterevidence, acceptable uncertainty, and whether a safe decision requires abstention or review. A third reviewer resolves differences using a logged rationale. Reviewers may retain an indeterminate reference when the time-bounded record cannot decide it; forced consensus is prohibited. Measure and report disagreement before resolution. A separate tool/provenance reviewer checks acquisition identity and authenticity where needed. The reference concerns what the available evidence justifies, rather than later physical truth or merely the EAL/2 evaluator's label.

Use EAL/2's actual `supported`, `contested`, `unsupported` and `out_of_scope` labels when scoring an EAL assessment, while mapping all arms to a predeclared common decision rubric. `Unsupported` means no usable derivation under the supplied record, not that the underlying proposition is false. Treat missing acquisition, invalid evidence, failed methods and uncertain external truth as distinct coded causes. Reference changes discovered after unmasking require a documented adjudication audit and a sensitivity analysis with the original reference retained.

## 4. Matched workflows

All arms receive the same neutral request, authenticated read-only tool catalogue, allowed records, information horizon, model snapshot, total wall-time and input/output/tool-call or monetary ceiling. They start with fresh context and cannot see another arm's work. The model matrix targets at least eight named snapshots, at least three providers and two snapshots on each *marginal side* of the declared size, reasoning, access and tool-interface axes; eight models cannot fill every intersection of those axes. If access or the information target prevents this, report named-model estimates and do not claim a model-class comparison. Randomise arm order within case × model blocks, balance call time across arms, and record actual resolved model revision, provider, reasoning effort, temperature, seed where supported, tool versions and token/cache accounting. Freeze retry and provider-outage rules. Resource caps constrain opportunities; actual use, latency and cost remain outcomes rather than quantities artificially equalised after the fact.

| Arm | Assigned operation | What it tests |
| --- | --- | --- |
| **P: strong plain prose** | A competent engineering prompt requests the claim, sources, query, scope, objections, uncertainty and a concise recommendation; the agent chooses tools and writes prose. No deterministic argument checker supplies a final answer. | Practical baseline with the same factual and tool access. |
| **T: Toulmin prose** | The agent uses separate one-line Claim, Grounds, Warrant, Backing, Qualifier and Rebuttal fields, selects tools and concludes in prose. No deterministic checker supplies a final answer. | Contribution of explicit argument prompts without a formal language. |
| **E: EAL/2 complete workflow** | The agent selects or authors the relevant family and parameter bindings, writes valid EAL/2 source, invokes permitted acquisition and assessment through the authenticated host, and communicates the host-owned final status with its limits. Invalid source, wrong family or absent packet remains an outcome. | End-to-end EAL/2 deployment, including its authoring and host boundary. |
| **J: generic checked structure** | The agent selects or authors an independent JSON/graph representation of the same claim, evidence, query, scope and objections; an equally capable generic checker produces a host-owned final status. | Whether structured checking and host control explain an apparent EAL/2 gain. |
| **E-text (optional diagnostic)** | Present EAL/2 text without executing its checker or enforcing a host-owned answer, under an otherwise matched prompt. | Conditional prompt-surface effect only; not part of the primary deployment comparison. |

Before confirmation, independently test E and J against the same valid, invalid, stale, wrong-query, cyclic, objection and alternative-derivation fixtures. Publish the coverage matrix and disagreements. Equal nominal status on a few cases does not establish semantic parity. If the independent checkers differ on a relevant case, E–J is a **system** contrast confounded by implementation and must be interpreted accordingly. A planned syntax-only sub-study must compare EAL/2 and meaning-equivalent JSON front ends through one shared typed backend, balancing length, examples and model familiarity; report it separately from E–P.

The trusted launcher must authenticate the case's principal and provide only grants for that case and arm. A model-proposed artefact ID or assessment ID is not an authorisation. The application displays the checked E or J status as its authoritative final state even when explanatory prose conflicts. Such enforcement is scored as an application property; it cannot be counted as correct model reasoning or faithful explanation. P and T must not be retrospectively given that enforcement when calculating their original end-to-end outcomes.

## 5. Actual tool execution and evidence identity

The read-only gateway supplies matched capabilities to each arm: pinned Git history and file queries; CI run, attempt and test reports; historical or live metric and log queries with unit, interval and aggregation; deployment or infrastructure state; and registered deterministic computations where the case requires them. Record the exact method version, input schema, tool argument, permitted time range, caller/grant, source system, query start and end, result or error, retrieval time, content digest, and any source authentication or signature validation. Pin code, container and adapter revisions. A digest detects later change in the captured bytes; it does not authenticate an untrusted collector or prove that a sensor measured the physical quantity claimed.

Retrospective adapters query immutable historical snapshots with an enforced `as-of` boundary. Never provide a later remediation, post-incident account or future metric as if it were available to the operator at the earlier decision. An isolated re-run of a test records the modern environment separately and must not masquerade as the historical CI result. Prospective adapters query the actual authorised system under a least-privilege read-only identity. Log permission denials, unavailable sources, API failures, rate limits and stale records. Each arm uses the same permitted access rule, while its independently chosen calls and actual errors are logged separately; no operator repairs only one arm's tool result after observing an answer.

Authoring EAL/2 or J source is allowed inside an isolated work area. Production repository commits, configuration changes, deployment actions, alert acknowledgements, messages to operators and other side effects are outside this protocol. Stop an attempt on an attempted unauthorised write, log it as an assigned failure and invoke the security response. Protected operational data supplied to model providers require approved data handling, retention and redaction; excluded sensitive cases remain visible in the sampling ledger.

## 6. Outcomes and estimands

The **primary attempt outcome** `Y=1` requires all of: relevant claim/family and parameters; admissible, correctly identified time-bounded evidence; a query and method that answer the stated question; a decision matching the independent bounded reference; and a final explanation that accurately states the decisive basis, material objection and qualification without contradicting the displayed checked status. Otherwise `Y=0`. The rubric must state which fields are mandatory for each case before unmasking. For an indeterminate reference, justified abstention can pass; indiscriminate abstention fails on cases with an adequate reference basis. Two masked scorers assess communication and grounds, recording disagreements and adjudication. Automated validation verifies formats and tool traces but does not substitute for engineering adjudication.

`F=1` marks an affirmative recommendation of reliance or release when the independent reference does not justify it. Report `F` per **all assigned adverse cases**, including malformed or missing outputs in the denominator, and separately the count among parseable outputs. Predeclare a minimum actionable decision-coverage threshold alongside the false-support limit, so refusing every case cannot pass the practical safety gate; the conjunctive primary outcome also counts unjustified refusal as failure. A host that suppresses contradictory prose can reduce final application `F` while still producing an inconsistent recipient explanation. Preserve raw and authoritative final outcomes separately.

Let `i` index cases, `m` frozen model snapshots, `r` repetitions and `a` assigned arms. The primary intention-to-treat (ITT) estimand is the case-population-weighted paired risk difference

`Δ_EP = E[Y(i,m,r,E) − Y(i,m,r,P)]`,

at the prespecified distribution of cases and equal prespecified weights over the enrolled model snapshots. `Δ_EJ` and `Δ_TP` use the corresponding paired differences. Estimate `Δ_EP` independently in retrospective and prospective stages; any combined estimate needs a separately frozen weighting rule and cannot replace those stage-specific results. A comparison over named snapshots does not establish a universal model-class effect. Marginal class analyses require at least two independently selected snapshots on each side, across providers where feasible, and a prespecified sampling interpretation; intersection effects need their own information calculation.

Secondary outcomes include false-support risk difference on adverse cases; valid-source submission; correct family retrieval and parameter binding; admissible acquisition; valid query and assessment; raw model-status agreement; authoritative final-status agreement; faithful explanation; appropriate abstention and decision coverage; time to usable decision; total model/API/tool cost including failed attempts, retries, caching and checker work; human authoring and review minutes; and decision quality per total cost. Preserve a failure cascade with the same assigned-attempt denominator, then report conditional diagnostics explicitly as conditional. Count provider outages both in ITT and in a separately labelled availability sensitivity analysis; never drop invalid EAL source or unavailable recipient packets from the primary denominator.

## 7. Information, analysis and decision rules

The pilot estimates paired discordance `q = Pr(Y_E ≠ Y_P)`, case-family intraclass dependence, adjudication disagreement, adverse-case prevalence, tool failure and cost variance. For an independent paired mean difference, an approximate 95% half-width `h` needs `n ≈ 1.96²(q − Δ²)/h²` paired cases; family clustering, unequal case weights and model repetition increase the required information. As an illustration only, `q=.30`, `Δ≈0` and `h=.10` imply about 116 independent pairs *before* inflation. The freeze must use simulation under plausible family effects, missingness, model drift and adverse strata to choose eligible **families and cases**, not a headline number of calls. If this information or sufficient real cases cannot be obtained, the stage is feasibility/descriptive, not confirmatory.

Predefine the target mixture of domains and statuses and use weights based on the eligible case sampling frame. Estimate within-model paired differences first; use family-cluster inference for within-model uncertainty, accounting for repeated states and assessment times. The primary pooled estimate uses frozen model weights and family-respecting uncertainty. With few model snapshots, report them as fixed named systems and avoid a population bootstrap over models or broad claims about model classes. Review model × arm and domain × arm interactions with wide uncertainty as secondary, with a declared multiplicity procedure for any confirmatory secondary claims. Diagnose family dominance, reference disputes, parity failures, missing tool logs and substantial time imbalance; show sensitivity to target weights, uncertain references, provider availability and alternative defensible scoring.

The freeze must specify a practically relevant minimum improvement `δ_b`, an acceptable upper bound on additional false-support risk `δ_s`, a minimum actionable decision coverage, confidence level, family-wise testing order and any prospective sample cap or sequential stopping boundary. Candidate planning values of ten percentage points for `δ_b` and two percentage points for `δ_s` are **not frozen thresholds**; domain owners must justify or replace them before case outcomes are opened. A two-sided interval overlapping both a useful improvement and harm is inconclusive. Failure to reject zero does not prove equivalence. Claims of equivalence between E and J require a separate, justified equivalence margin and adequately precise interval.

| Observed region after predeclared diagnostics | Interpretation and next action |
| --- | --- |
| `Δ_EP` exceeds the frozen benefit criterion, adverse false-support risk and actionable decision coverage meet their frozen conditions, tool/reference/parity checks pass, and shadow findings do not reverse the result | Support a bounded workflow advantage for the tested settings; replicate in new systems before generalising. `Δ_EJ` governs whether a generic checker is an equally effective alternative. |
| E exceeds P but E and J remain equivalent within a justified precision and parity holds | Attribute the observed practical advantage to checked structure/host workflow within the tested scope; no EAL/2-specific notation claim. |
| Host status matches its own represented source while E fails source authoring, family selection, evidence or explanation | Report the host enforcement property and the failed end-to-end outcome separately; repair the failed stage before a new efficacy test. |
| E increases false support beyond the safety criterion, or the primary effect favours P with sufficient precision | Weaken the deployment claim and investigate the failure mode; do not promote the workflow. |
| E–P or E–J intervals span material benefit and harm; cases are too few or models disagree materially | Inconclusive; report estimates and uncertainty, then design a larger or narrower investigation. |
| Reference adjudication is unreliable, a tool did not execute authentically, historical information leaked, checker parity fails for an E–J attribution, or a freeze/ethics rule is broken | Suspend the affected inferential claim; retain attempted outcomes and audit or rerun only under a newly versioned protocol. |

The matrix distinguishes the scientific claim, the operational adoption decision and any later intervention authorisation. A correct host label against a reference derived from the same EAL source is circular evidence; independent reference and real acquisition are required.

## 8. Audit, safety and reporting

Archive the eligible and excluded case ledger; protected adjudication and disagreements; manifests, neutral and arm-specific briefs; source/graph artefacts; prompt hashes; random order; model request IDs and resolved revisions; tool call traces and errors; checker and host decisions; raw and authoritative final answers; scoring records; analysis scripts; actual charges, human effort and protocol deviations. Keep secrets and personal/operational data in approved restricted storage, releasing only a privacy-safe manifest and aggregate results. Version every post-freeze amendment, identify which outputs were inspected before it, and keep the original analysis alongside any amended exploratory analysis.

The operator or security owner may stop any attempt for unauthorised access, data exposure, unstable infrastructure or a forbidden write. Routine bad recommendations remain private observed outcomes rather than stopping the study or influencing the real operator. No conclusion about improved physical safety, human cognitive bias, faster releases or production action quality follows from this read-only agent study alone. Report pilot, retrospective replay and prospective shadow separately, including negative and null outcomes; never describe this protocol as an executed experiment until its ledgers and adjudications exist.
