# Kubernetes resource revision: a synthetic EAL/2 argument

The [source](../kubernetes-resource-revision.eal) describes an invented `payments/checkout-api` deployment. No Kubernetes cluster was queried. Three immutable input examples and an executable test check how an authored argument changes when another engineer deploys a CPU-intensive batch workload on the same node. The represented result is a bounded assessment of submitted observations; it is neither a proof of application correctness nor a guarantee of future service performance.

## Engineering question and observations

The first engineer builds commit `9f4c7a1`, deploys its pinned image to three ready endpoints and runs a five-minute `checkout-create` trial targeting `checkout-pod-7` with a configured 200-requests-per-second target. The example retains 10,000 reported sampled binary response outcomes and four p99 latency samples at 0, 100, 200 and 300 seconds. A full 300-second run at that target would offer 60,000 requests; these fixtures do not record achieved rate, all eligible requests or how the 10,000 were selected. The computed Wilson lower 95% bound must exceed 0.998, and every sampled p99 must be at most 150 ms. The claim about the canary refers to that finite sample and target Pod. The separate `provisional_operating_basis` claim asks whether those observations, rollout identity and current capacity records give an uncontested basis to *consider* operating this Pod and build for another fifteen minutes under an unchanged profile. The future interval itself is not mechanically verified.

| Revision | Current sampled result | Scheduler request headroom | Co-tenant observation | Raw EAL status | Example host gate |
| --- | --- | ---: | --- | --- | --- |
| 10:30, before batch job | Success and latency criteria met | 1,200 millicores | Complete nonfinding for named Pod/node/window | `supported` | `accepted` |
| 11:30, batch deployed | Success and latency criteria still met | 1,100 millicores | Batch uses 2,900 millicores against a 200-millicore request; target cgroup throttle ratio 0.28 | `contested` | `contested` |
| 12:30, mitigation and fresh trial | Success and latency criteria met again | 2,100 millicores | Complete nonfinding for a new named window | `supported` | `accepted` |

The first canary result remains a historical observation. The second revision contests an inference about continued operation; it does not retroactively make the earlier sample false. A fourth test changes the 11:30 latency sample to 185 ms and finds the canary and operating basis `unsupported`. An old rollout record fails the three-minute freshness bound. Changing the cluster UID makes the claim out of scope. These outcomes are executable tests of the represented relation, not empirical Kubernetes results. The after-mitigation fixture reports lower batch CPU usage and a fresh nonfinding. It does **not** establish that the batch Pod was relocated, that a CPU limit was installed or enforced, or that the condition will persist. Those assertions would require their own deployment, placement, limit and intervention evidence.

Kubernetes schedules CPU on **requests**, while the CPU request typically supplies a weight under contention; a CPU limit is enforced separately. A request-headroom snapshot therefore cannot show that an under-requested batch container is harmless to a latency-sensitive neighbour. The Kubernetes documentation also identifies HPA as a periodic controller which computes CPU utilisation against the resource request. [Resource management](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/) and [horizontal autoscaling](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/) specify these distinct mechanisms. Deployment readiness and progress conditions report controller state; they do not measure application latency. See the [Deployment conditions](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/) documentation.

## Evidence another engineer would need

| Proposition or possible defeat | Read-only acquisition contract | What that record can establish | Additional inferential work |
| --- | --- | --- | --- |
| The implemented source corresponds to running Pods | Verify source commit, build provenance, image digest and signature under a named trust root; read Deployment UID/generation, ReplicaSet/Pod UIDs and `imageID`, Service selector and EndpointSlice membership | Identity correspondence at the observation time, if signature and API provenance are checked | Code review, specifications and tests must address behavioural correctness; readiness is not an SLO result |
| The bounded canary met its conditions | Record load generator inputs, route, request mix, 300-second window, sent/eligible/selected request counts and IDs, achieved rate, sampling rule, response outcomes, independent end-to-end latency histogram, missing samples and clock units | The stated finite sample and numerical calculation, if the generator ledger is trustworthy | Review generator/telemetry coverage, selection and measurement error; the Wilson calculation assumes a binomial sampling model |
| The target has current resource capacity | Read Node UID and allocatable CPU; list all Pod requests, limits, placement and HPA state; record a coherent observation interval | Scheduler's request accounting for identified Pods | Compare actual CPU usage, throttled periods, memory pressure, queue depth and scaling lag. Node requests omit processes outside kubelet's accounting; see [Nodes](https://kubernetes.io/docs/concepts/architecture/nodes/) |
| The later batch deployment changes the inference | Correlate audit/watch event, batch Pod UID and start time, placement, resource request/limit, batch CPU usage, checkout throttle/queue/latency series and traffic mix | A temporally and spatially matched challenge to the operating warrant | Establish whether batch activity explains the change. Correlation and a complete `kubectl get` snapshot alone cannot identify the causal effect |
| Mitigation restores the profile | Bound or relocate the batch Pod, repeat the same load and endpoint measurement, and monitor the same Pod/node identities for the declared window | A new observed result with a different resource condition | Compare matched periods, account for HPA/restarts and request mix, and do not reuse the old result as a substitute |

Production adapters must use a pinned cluster identity, namespace, object UIDs, resource versions where relevant, exact tool requests and measurement times; collection errors and incomplete watch coverage must remain explicit. A Kubernetes API adapter and a metrics adapter would bind these records to source declarations, while the host would retain the full trace and give recipients a short claim-specific explanation. The fixtures in this directory exercise imported JSON observations through the real `ReasoningService` and do not establish the trustworthiness of such adapters or of a cluster.

The built-in `inductive/1` and `temporal/1` methods accept exact numerical payload shapes. The example therefore carries measurement identity in each tool observation envelope's `details.measurement_identity`: trial ID, Pod and node UIDs, 300-second window, series kind and ID, plus the canonical digest of that observation's numerical payload. The separate sampling and telemetry manifests repeat the series ID and payload digest. The host gate matches these fields and recomputes each numerical payload's digest. Wrong trial, Pod, window, series or attached payload returns `unresolved` even if the raw numerical EAL calculation is `supported`. This is a consistency binding, not proof that the producer labelled its series truthfully. A party able to change both measurement and manifest could still fabricate a coherent record; production would need trusted acquisition, authorised query labels and independently checked provenance.

The strongest causal check would predeclare a controlled intervention: hold checkout image, traffic generator, request mix, target placement and HPA settings fixed; randomise short periods with the batch workload admitted or isolated, leave washout time and measure checkout latency, throttling and errors with an independent observer. Analyse the period-level paired contrast and carry over possible order effects. A second experiment can repeat after a CPU limit or dedicated-node placement. The intervention supports a bounded causal claim if its isolation, timing, measurement and interference assumptions are defended. The present `structured/1` composition does not perform that analysis; merely adding a collected time series would leave the causal warrant authored.

## Formal and operational limits

The EAL/2 evaluator computes the Wilson bound and finite sampled temporal predicate, checks evidence identity and age, propagates declared premises and applies an authored objection to the operating reasoning step. It labels the objection `active` at 11:30 and the root `contested`; it keeps the independent canary observation `supported`. An assessment always reports `prose_verified: false`. Evidence digests check consistency with recorded JSON, not the source's authenticity or physical truth. The `signature_verified` and `complete` fields in the synthetic fixtures are assertions; a production verifier must establish them under an explicit trust configuration.

One negative test deliberately drops the contention record at 11:30. The current evaluator then reports the operating basis `supported`, because it only evaluates submitted authored attacks. The example [host gate](../kubernetes_resource_gate.py) preserves that result as `raw_eal_status` but returns `unresolved`. Before returning `accepted`, it requires every mandatory acquisition with the pinned source/request/context/tool identity, an `ok` status, fresh observation time and matching value digest. It checks that response and latency payloads are bound to the same 300-second trial and target Pod as their manifests; that Kubernetes and monitor records identify the same Pod and node; and that a completed monitor query agrees with the contention record and predeclared threshold. Missing, failed, stale or incoherent monitoring returns `unresolved`. A qualifying attack produces `contested`. The gate re-evaluates the fixed source and does not accept a recipient-supplied status.

This fixture-specific gate does not authenticate a cluster observation, establish that a `query_complete` assertion reflects a genuinely exhaustive query, or prove that the selected signal detects every possible interference mechanism. A production collection manifest must report the interval, source query and cardinality, with independent access and provenance controls. Dynamic Pod placement, resource changes, admission, HPA, node pressure and traffic-profile changes should invalidate the near-term basis and trigger recollection. TTL alone does not prove physical continuity. A separate human or authorised decision remains necessary where the operating process requires it.

EAL/2 here is an authored argument dependency graph with grounded acceptability labels over explicitly supplied objections. It does **not** instantiate ASPIC+. ASPIC+ requires a selected logical language and contrariness relation, strict and defeasible rules, premise categories, argument construction, preference rules and an attack-to-defeat relation. The distinction between undermining a premise, rebutting a defeasible conclusion and undercutting a defeasible inference is defined in [Modgil and Prakken's ASPIC+ tutorial](https://doi.org/10.1080/19462166.2013.869766). The contention observation in this example acts as an authored attack on an inference; the current engine does not prove that the observation entails the attack or compare its preference to a contrary argument.

This case does not yet require a full ASPIC+ implementation: the named interference challenge, alternative evidence and missing-observation failure are the immediate engineering issues. If independently adjudicated cases require formal rule priorities and systematic contrary-argument generation, an optional, versioned host method could implement a **specified finite ASPIC+ profile** with typed input, generated arguments, a transparent defeat trace and bounded grounded semantics, without changing EAL/2 grammar. The method would need an explicit binding from its conclusions to EAL claims and a visible authoring form; opaque JSON carrying an entire unreviewed theory would reproduce the current inferential gap. The solver would settle the encoded conflict semantics, while acquisition completeness, authenticity, statistical identification and source-to-claim correspondence would remain separate obligations.
